# WakeLux

Автояркость по камере и включение экрана при подходе — для Android-планшетов без датчика освещённости.

[English version](README.md)

**❤️ Поддержать проект:** если хотите поддержать дальнейшую разработку, см. [`SUPPORT.md`](SUPPORT.md).

## Зачем

Дешёвый планшет — очевидный кандидат на роль настенной панели Home Assistant, и у многих из них нет датчика освещённости. Если `android.sensor.light` отсутствует, Android вообще не показывает переключатель автояркости, и экран остаётся на том уровне, который вы выставили руками: днём тускло, ночью слепит. Вторая беда обратная скринсейверу — панель должна быть тёмной, пока к ней никто не подходит.

WakeLux закрывает обе задачи фронтальной камерой. Раз в секунду берётся один кадр превью: среднее по Y-плоскости даёт оценку освещённости, разница с предыдущим кадром — движение. Двух чисел в секунду хватает, чтобы вести `Settings.System.SCREEN_BRIGHTNESS` и дёргать короткий wake lock.

Поток кадров не выходит за пределы `onPreviewFrame`. Кадры не сохраняются, не кодируются и никуда не отправляются — буфер переиспользуется и затирается каждую секунду. При включённой интеграции с Home Assistant по сети уходят только числа.

## Требования

- Android 6.0 (API 23) или новее
- рабочая фронтальная или тыловая камера
- разрешения `CAMERA` и `WRITE_SETTINGS`
- root не обязателен, он включает только дополнительные возможности из отдельного раздела

Разрабатывалось на Lenovo TB-X103F (MT8163, 1 ГБ RAM, Android 6.0.1), который круглосуточно работает панелью Home Assistant.

## Установка

```bash
./gradlew :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

`WRITE_SETTINGS` — это appop, а не рантайм-разрешение, поэтому `pm grant` для него не работает. Либо кнопка в приложении, либо оба разрешения через adb, что удобнее для планшета, уже прикрученного к стене:

```bash
adb shell pm grant com.vasmarfas.wakelux android.permission.CAMERA
adb shell appops set com.vasmarfas.wakelux WRITE_SETTINGS allow
```

## Настройка

Запустите сервис на первой вкладке. Появится уведомление с живыми значениями (`в комнате 125 · экран 176 · изменения 0,0% · тихо`) — Android всё равно требует уведомление для фонового сервиса, так пусть оно будет полезным.

Дальше калибровка под комнату, это минута работы:

1. Закройте камеру рукой и посмотрите *Свет в комнате* на вкладке **Сейчас**. Это нижняя граница.
2. Уберите руку, запомните значение при обычном освещении. Это верхняя.
3. Впишите оба числа в *Уровень «тёмная комната»* и *Уровень «светлая комната»* на вкладке **Настройки**.

Значения по умолчанию (10 и 180) намеренно широкие. На тестовом планшете реальный диапазон оказался 3–130, то есть с дефолтной верхней границей экран никогда не вышел бы на полную яркость. Автоэкспозиция сжимает диапазон, это ожидаемо, и именно поэтому калибровка делается под помещение, а не берётся из таблицы люксов.

Между двумя точками яркость идёт по прямой. Если нужна другая реакция — ровно днём и резче в сумерках — на вкладке **Кривая** можно расставить произвольные точки.

## Пробуждение: присутствие и близость

Один порог движения в жилой комнате бесполезен. Чувствительности, достаточной чтобы поймать проходящего мимо человека, хватает и на шевеление на диване, и панель горит весь вечер. WakeLux считает по одной и той же разнице кадров два порога:

| Настройка | Что делает | По умолчанию |
|---|---|---|
| Считать присутствием изменения от | Не даёт погаснуть уже включённому экрану, питает датчик движения в Home Assistant | 2 % кадра |
| Будить экран только при изменениях выше | Единственное, что включает экран | 12 % кадра |

Разделение работает, потому что доля кадра — приличная замена расстоянию: человек в полуметре от камеры занимает заметную часть кадра 160×120, человек в другом конце комнаты — единицы процентов. На тестовой установке шевеление сидя не превышало 1 %, а подход уверенно перекрывал порог в 12 %.

Настройка эмпирическая, и вкладка **Сейчас** делает её простой: строка *Изменения в картинке* показывает живой процент. Пошевелитесь так, как обычно сидите, запомните число, подойдите к планшету, запомните снова — порог пробуждения ставьте между ними.

Если процентами разделить не выходит (в кадре коридор или телевизор), включите *Реагировать только на середину картинки*. Тогда решение о пробуждении принимается по центральному прямоугольнику кадра, а отладочный просмотр обводит его зелёным, чтобы было видно, что учитывается.

На устройствах с датчиком приближения его можно включить как дополнительный триггер. У большинства планшетов такого датчика нет — вкладка **Сейчас** показывает, есть ли он у вашего.

Одно жёсткое ограничение: в полностью тёмной комнате камере не с чем работать, и подход не определится. При тусклом свете всё в порядке. Шум матрицы при штатном пороге пикселя измерен как 0.00 % кадра, поэтому порог темноты можно держать на уровне 2 без ложных пробуждений.

## Home Assistant

Приложение умеет отправлять свои числа в `/api/states`, превращая планшет в датчик освещённости и присутствия для комнаты, где он висит.

1. В Home Assistant откройте профиль → **Безопасность** → **Долгоживущие токены доступа** и создайте токен. **Он должен принадлежать учётной записи администратора** — запись состояний через REST API требует прав админа, и токен обычного пользователя вернёт `401 Unauthorized`, хотя читать им можно.
2. В WakeLux впишите базовый URL (`http://homeassistant.local:8123`), вставьте токен, включите интеграцию и нажмите *Отправить тестовое значение*. Результат появится прямо под кнопкой.

Создаваемые сущности, где `wakelux` — настраиваемый префикс:

| Сущность | Что это |
|---|---|
| `sensor.wakelux_luma` | освещённость в комнате, 0–255 |
| `sensor.wakelux_brightness` | текущая яркость экрана, 0–255 |
| `binary_sensor.wakelux_motion` | движение перед планшетом, `device_class: motion` |
| `binary_sensor.wakelux_screen` | включён ли экран |
| `sensor.wakelux_status` | состояние камеры; кадры, перезапуски, пробуждения и время работы в атрибутах |

Значения уходят по интервалу и сразу же при изменении движения или состояния экрана.

Сущности, созданные через REST API, не попадают в реестр сущностей и исчезают при перезапуске Home Assistant, возвращаясь со следующей отправкой. Это особенность `/api/states`, а не приложения. Если нужно, чтобы они переживали перезапуск, поставьте мост через MQTT.

## Если планшет работает киоском

- Если ваше киоск-приложение само управляет яркостью (Fully Kiosk это делает в Device Management), выключите это. Яркость на уровне окна перекрывает системное значение, которое пишет WakeLux. Проверяется так: `adb shell dumpsys power | grep mScreenBrightnessOverrideFromWindowManager`, должно быть `-1`. Приложение Home Assistant яркость окна не трогает.
- Сервис поднимается по `BOOT_COMPLETED`. Части прошивок нужен белый список автозапуска — перезагрузите планшет и проверьте, вернулось ли уведомление.
- Погасить экран публичным API нельзя, поэтому WakeLux пишет `SCREEN_OFF_TIMEOUT` (по умолчанию 30 с) и отдаёт это системе. Исходное значение возвращается при остановке сервиса.

## Управление снаружи

Любое действие и любая настройка доступны через broadcast, что удобно для скриптов и shell-команд Home Assistant:

```bash
adb shell am broadcast -a com.vasmarfas.wakelux.COMMAND --es cmd status
adb shell am broadcast -a com.vasmarfas.wakelux.COMMAND --es cmd set --es key wake_motion_ratio --es value 0.25
```

Команды: `start`, `stop`, `status`, `wake`, `screen_off`, `restart_camera`, `set`, `export`, `import`, `reset`, `csv`. `status` отдаёт JSON со всем, что приложение видит. Если задать пароль в настройках, к каждой команде добавляется `--es token <значение>`.

Android не доставляет broadcast приложению, которое ни разу не запускали или которое остановили принудительно, — откройте его один раз после установки.

## Возможности с root

Все необязательные и по умолчанию выключены:

- писать системные настройки через `su`, если `WRITE_SETTINGS` так и не выдали;
- выдавать себе `CAMERA` и `WRITE_SETTINGS` при старте;
- гасить экран через N секунд бездействия, не дожидаясь системного таймаута, — пригодится, если экран удерживает другое приложение.

## Как это устроено

Camera1 (`android.hardware.Camera`), не CameraX и не Camera2. На целевом железе Camera2 HAL сообщает уровень `LEGACY`, то есть Camera2 был бы обёрткой над тем же кодом с лишними слоями. Камера открывается один раз, превью привязывается к закадровой `SurfaceTexture`, кадры приходят через `setPreviewCallbackWithBuffer` с тремя переиспользуемыми буферами — аллокаций на кадр нет. Размер превью берётся наименьший из доступных (здесь 160×120).

Один проход по Y-плоскости даёт среднее, счётчик изменившихся пикселей и, если включена зона пробуждения, тот же счётчик по центральному прямоугольнику. Кадры больше 65 536 пикселей прореживаются по шагу, поэтому переключение на тыловую камеру не обрушит процессор. Замеры на MT8163: 1–2 % на процесс приложения плюс 8–10 % на `mm-qcamera-daemon` — это цена постоянно открытого превью, и снизить её из приложения нельзя, у HAL нет фиксированного низкого fps-диапазона.

Пробуждение — `SCREEN_BRIGHT_WAKE_LOCK | ACQUIRE_CAUSES_WAKEUP | ON_AFTER_RELEASE` с таймаутом. Deprecated с API 17 и до сих пор единственный способ разбудить экран без root и прав владельца устройства.

Для круглосуточной работы предусмотрены три уровня восстановления: watchdog внутри потока камеры перезапускает конвейер, когда кадры прекращаются; error callback отрабатывает смерть HAL; сервис следит за меткой времени состояния контроллера и пересоздаёт контроллер вместе с потоком, если она не меняется 90 секунд. Последнее закрывает случай зависшего нативного вызова, когда внутренний watchdog тоже не выполняется. Все интервалы считаются по `SystemClock.elapsedRealtime()`: у планшета без батареи стенные часы после загрузки прыгают на десятилетия при синхронизации времени, и всё, что измерялось через `currentTimeMillis()`, ломается незаметно.
